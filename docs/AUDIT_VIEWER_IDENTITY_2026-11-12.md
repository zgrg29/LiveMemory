# 专项审计：Bilibili 观众身份与独立观众统计

日期：2026-11-12
范围：观众身份识别、UID 解析、消息存储、独立观众统计、直播历史 / AI 分析中心跨页面一致性
数据库：`E:\新建文件夹\database\livememory.db`（schema 13，只读审计；未修改用户数据库）
审计对象场次：`ses_01M75S69P4H0NSX87PD4`（Bilibili，2026-11-12 01:06:20 → 02:55:46）

## 0. 结论（先给答案）

1. **这场直播只有 2 名「可识别观众」，不是数据库丢失或 JOIN 过滤。** 726 条弹幕全部没有平台 UID（`viewer_uid`/`viewer_id` 均为 NULL），只有 1 条 Super Chat 和 2 条大航海事件带 UID；去重后正好 2 个有效 UID，`viewer_sessions` 也正好 2 行。
2. **原始库实际保存了 2 个不同的有效用户身份**：`bilibili:3462368`（书落书愿，Super Chat 200 元）和 `bilibili:11628777`（大统领修新配，2 条大航海）。这两个人不是弹幕发言者。
3. **这是 Bilibili 平台侧的匿名化/风控问题，不是 YouTube 问题，也不是所有平台的统计逻辑问题。** 两场 Bilibili 记录都出现 100% 弹幕无 UID；四场 YouTube 记录的弹幕 UID 覆盖率接近 100%。
4. **代码层的直接原因**是平台行为与产品表述叠加：
   - Bilibili 未登录 WebSocket 连接收到的是打码昵称（`文***`）和 `uid=0`；本地 mapper 按设计把 `0` 视为「无身份」，不猜测、不合并；
   - 页面把「有稳定 UID 的互动用户数」标成「独立观众 / 本场参与人数」，且完全不显示 726 条未识别消息，造成「727 条消息只有 2 个观众」的误导。
5. **没有历史身份数据丢失**：这 726 条消息的 UID 从未被平台提供，不是本地删除；消息原文、时间、计数都在。
6. **历史统计可以重算消息数/时间线/身份覆盖率，但不能恢复这 726 条消息的真实观众身份。** 打码昵称不稳定且会碰撞，不能用于合并或反推。
7. 修复只做最小必要改动：统一「可识别观众」口径、显式展示「未识别身份消息」、补充登录说明、并在 canonical 层防御 `uid=0` 被误建为同一个观众。**没有为了增加人数而伪造或推断任何身份。**

| 层 | 结论 | 证据 |

| 前端缓存/刷新 | 关闭并重启服务后重新查询同一数据库，结果仍为 2 / 726 | 本轮用数据库副本启动服务实测 |

### 2.1 不是这些原因

- **不是 UID 字段名不一致**：Bilibili mapper 读取 `info[2][0]`；本库中带 UID 的 SC/guard 都能落成 `viewer_uid`。
- **不是 UID 类型转换**：`stable uid` 被 `String()` 统一；同一个 UID 的数字/字符串形式不会拆成两个人。
- **不是把不同用户合并**：本场没有任何 `bilibili:0` 或按昵称生成的 viewer；`viewer_sessions` 只有 2 个真实 UID。
- **不是把缺失 UID 归入同一个用户**：缺失 UID 的事件 `viewer_id=NULL`，不进入 `viewer_sessions`。
- **不是只识别某类弹幕**：726 条 `chat` 全部被记录；问题在身份字段，不在事件被过滤。
- **不是只统计已建立档案的用户**：`unique_viewer_count` 是「本场有稳定 UID 的互动者」，包括只有礼物/SC/大航海、没有发言的人；这正是「可识别观众」，不是「所有发言者」。
- **不是 JOIN/过滤丢人**：`viewer_sessions` 的 2 行与 `events` 中 2 个 distinct `viewer_uid` 完全对应；没有孤儿。
- **不是历史迁移**：schema 13；该场是 2026-11-12 新写入，不是旧数据迁移结果。
- **不是前端缓存**：副本服务重启后数字不变。

## 3. 统计口径：目前混用了哪些概念

| 概念 | 本场值 | 定义 | 备注 |
| --- | ---: | --- | --- |
| 独立互动观众（可识别） | 2 | 本场有稳定平台 UID 的互动用户，含发言/礼物/SC/大航海 | 当前 `uniqueViewerCount` 实际含义 |
| 可识别观众 | 2 | 同上 | AI 中心的写法是正确的 |
| 已建立观众档案的用户 | 2 | `viewers` 中与本场有 `viewer_sessions` 的用户 | 与上一行同集 |
| 发言用户 | 1 | `viewer_sessions.message_count > 0` 的用户 | 本场只有 SC 用户；弹幕发言者全部不可识别 |
| 送礼用户 | 0 | 有 gift 事件且身份可识别 | 本场没有礼物 |
| SC 用户 | 1 | 有 Super Chat 的用户 | `bilibili:3462368` |
| 大航海用户 | 1 | 有 guard 事件的用户 | `bilibili:11628777` |
| 平台提供的观看人数 | 未知 | 平台 `online`/人气值，不是独立观众 | 本场历史表未保存该值；不能用弹幕反推 |
| 未识别身份消息 | 726 | 消息事件中 `viewer_uid` 为空的数量 | 本轮新增显式指标 |

**建议的产品定义（已按此修复）：**

- **可识别观众** = 本场至少一条事件带稳定平台 UID 的去重人数；包含只送礼/只 SC/只大航海的用户，不要求发言。
- **未识别身份消息** = 本场 chat + Super Chat 中作者 UID 缺失的条数；仍计入消息总数、时间线和 AI 输入，但不计入可识别观众。
- **实际观看人数** = 平台提供时才展示，且明确标注为平台口径；没有时显示「未知」，绝不由弹幕数推断。
- **发言用户** = 可识别观众中 `message_count > 0` 的子集；与「可识别观众」分开命名。

## 5. 修复内容（最小必要）

### 5.1 canonical 层防御 `uid=0`

- `src/shared/events.mjs`：
  - `buildViewerId()` 将 `0` / `"0"` 视为无身份；
  - `normalizeEvent()` 将 `viewer_uid` 的 `0` 规范为 `null`。
- 目的：即使未来某个适配器把平台的 `0` 直接传下来，也不会创建 `platform:0` 这个「所有匿名观众共用」的假档案。Bilibili mapper 原本已做同样判断，本轮只是把规则下沉到唯一事件模型入口。

### 5.2 新增「未识别身份消息」派生统计

- `src/storage/repositories/sessions.mjs`：`SESSION_SELECT` 增加 `unidentified_message_count`（只统计 `chat` / `super_chat` 且 `viewer_uid` 为空）。
- `src/storage/repositories/monitor-targets.mjs`：监控场次列表同样返回该字段。
- `src/analytics/sessions/summary.mjs`：输出 `identifiedMessages`、`unidentifiedMessages`、`identityCoverage`、`identityComplete`。
- `src/analytics/sessions/history-search.mjs`：历史搜索结果加入 `unidentifiedMessageCount`。
- `src/server/serializers.mjs`、`src/server/routes.mjs`：HTTP 返回同名 camelCase 字段。
- 该指标是从原始 `events` 每次查询实时计算的，**历史数据自动重算，不需要迁移、不修改任何事件行**。

### 5.3 统一页面口径与警告

- 直播页 / 直播历史 / AI 分析中心统一使用「可识别观众」，并在有未识别消息时显示：
  - 直播页：统计卡下方警告，说明 726 条消息没有 UID、不会被计入观众；
  - 历史列表：每行显示「726 条未识别」徽标；
  - 历史详情：独立警告卡，显示总消息、未识别消息，并提示 Bilibili 未登录风控；
  - AI 分析中心：任务规模新增「未识别身份消息」行，并提示长期画像只覆盖 2 位可识别观众。
- 修正了原本文案「登录不会改变观众的身份字段」——Bilibili 未登录风控正是导致身份缺失的原因，这句话是错误的。
- 登录标题从「可选」改为「建议」；未登录状态明确提示「平台可能隐藏弹幕 UID，观众统计会不完整」。
- 未改名「可识别观众」的统计值、没有修改 `message_count`、没有删除/合并任何观众档案。

### 5.4 未做的修复（有意为之）

- **没有**把打码昵称当成身份，**没有**按昵称前缀合并，**没有**为 726 条弹幕虚构 UID。
- **没有**删除或重写历史 Bilibili 记录。
- **没有**修改 AI 分析逻辑、金额逻辑、去重逻辑。
- **没有**自动替用户登录；登录仍由用户在直播页扫码完成。

## 6. 根因证据的外部对照

Bilibili 在 2023 年引入弹幕风控：未登录连接下，弹幕用户名会变成 `A***` 形式，数据中的 `uid` 变为 `0`；为录播姬等工具添加登录 Cookie 可解除该限制。

- [解决录播姬的 B 站直播弹幕用户名变星号的办法及注意事项](https://www.bilibili.com/opus/846907189335425030)
- [blivechat Issue #111：新策略影响下无法获取用户名，对策讨论](https://github.com/xfgryujk/blivechat/issues/111)

本项目 `docs/PLATFORM_INTEGRATIONS.md` 也早已记录过真实房间 `5050` 的 72/77 条弹幕 `UID=0` + 昵称打码；当时把它当作「真实存在的身份不完整」，但没有把「整场 100% 缺失时的用户可见警告」补齐。本轮补的是产品层可见性，而不是伪造数据。

**证据限制（必须如实说明）：** 本项目不保存原始 WebSocket 帧（隐私设计），因此无法在本机重新读取 2026-11-12 那 726 条消息的原始 `info[2][0]` 数值。以上结论由三部分证据共同支持：库内 726/726 的 `viewer_uid=NULL` + 全打码昵称 + 付费事件真实 UID；同一份代码当前对正常房间能解析出真实 UID；Bilibili 风控的公开行为记录。没有把「推断」写成「已抓到原始帧」。

## 9. 历史数据能否重新计算

| 项目 | 能否重算 | 说明 |
| --- | --- | --- |
| 消息数、礼物数、SC/大航海数 | ✅ | 原始 `events` 行完整 |
| 时间线、峰值、活跃时长 | ✅ | 原始 `occurred_at` 完整 |
| 可识别观众数 | ✅ | 从 `viewer_sessions` 重算，仍为 2 |
| 未识别消息数 / 覆盖率 | ✅ | 本轮新增派生指标，自动重算 |
| 726 条弹幕的真实观众身份 | ❌ | 平台从未提供 UID；打码昵称不稳定且会碰撞 |
| 实际观看人数 | ❌ | 本场历史未保存平台 `online` 值；不能用弹幕推断 |

因此：历史数据「足够重算统计」，但**不足以恢复身份**。任何声称能从打码昵称还原 71 个真实用户的做法都不可靠，本轮明确拒绝。

## 10. 残余风险与未验证

- **登录是否能 100% 解除 Bilibili 风控**：本轮没有可用的 Bilibili 账号 Cookie，无法实测「登录后同一房间恢复真实 UID」。外部资料与官方工具行为支持这一结论，但平台策略可能变化；修复后的界面只提示「建议登录」，不承诺 100%。
- **原始帧未保存**：无法从本机日志重新提取 2026-11-12 的原始 `uid`；结论依赖库内签名与外部行为证据。
- **平台在线人数**：历史表没有保存 `online`/人气，无法给出「实际观看人数」。
- **真实浏览器视觉**：未做截图验收；i18n/结构/HTTP 已有测试。
- **其他平台**：YouTube 当前 0 未识别消息；若未来 YouTube 也出现缺失身份，同一套警告与派生指标会自动生效。
