# 技术决策记录（DECISIONS / ADR）

## ADR-001 独立新仓库，参考旧项目只读

**状态**：已采纳
**背景**：`bili-gift-drop` 已有 Bilibili 登录、WebSocket、礼物与多语言实现，但产品目标不同（礼物特效 vs 长期记忆），且不能破坏旧项目。
**决定**：新建 `LiveMemory` 仓库；旧项目克隆到 `.ref/bili-gift-drop`（gitignore），只读参考，不修改、不复制其业务规则。
**后果**：协议实现可借鉴，但必须重新用真实直播验证；文案与 UI 完全独立。

## ADR-002 使用 Node 内置 `node:sqlite`

**状态**：已采纳
**背景**：SQLite 原生模块（better-sqlite3）需要 node-gyp/预编译二进制，会显著增加 Windows 打包与用户机器兼容风险。
**决定**：使用 Node 22.5+ 自带的 `node:sqlite`（同步 API、WAL）。
**后果**：
- 运行时零原生依赖，SEA 打包可直接复用官方 node.exe；
- 仍标记为实验特性，Node 版本必须 ≥ 22.5，启动器显式检查；
- 无 `db.backup()`，M5 用 `VACUUM INTO` 做一致快照。

## ADR-003 Windows EXE 使用 Node SEA + postject

**状态**：已采纳（本机验证）
**背景**：electron-builder 体积大；pkg/nexe 对 ESM 与内置模块支持不稳；原生模块打包复杂。
**决定**：SEA 注入应用资源，bootstrap 解压后调用现有启动器。
**后果**：
- 产物约 90 MB（含完整 Node 运行时）；
- 首次运行需解压 64 个资源文件；
- 需要构建期 postject，固定版本并校验 SHA-256；
- 必须把 PE 子系统改为 Console 才能满足可见命令行需求。

## ADR-004 运行时零依赖、前端无构建

**状态**：已采纳
**背景**：面向长期维护与打包稳定性，避免供应链与构建工具腐烂。
**决定**：不使用 npm 运行时依赖；前端原生 ES Modules + CSS 变量，无打包器。
**后果**：需要自己实现 ZIP、图表、i18n、路由等小工具；换来可审计、可打包、无构建步骤。

## ADR-005 设置存 JSON，业务数据存 SQLite

**状态**：已采纳
**背景**：启动器需要在数据库打开前知道语言偏好；数据库损坏时仍应能显示本地化错误。
**决定**：`config/settings.json`（原子写、校验、损坏备份）保存语言/主题/存储模式/端口；其余全部入库。
**后果**：两处状态源，但职责清晰；语言偏好不会被数据库故障阻塞。

## ADR-006 单一事件写入管线

**状态**：已采纳
**背景**：去重、金额、观众聚合若分散在路由/适配器，极易重复计数。
**决定**：所有事件经 `EventIngest.record()`，单事务内完成插入、身份、聚合、计数。
**后果**：平台适配器只产事件；重复投递天然被唯一键拦截；测试集中在一个入口。

## ADR-007 金额使用整数 minor units + currency + value_kind

**状态**：已采纳
**背景**：浮点会累积误差；礼物“展示价值”与“实际支付”可能不同；多币种不能相加。
**决定**：`amount_minor`、`unit_amount_minor` 为整数；`currency` 为 ISO-4217；`value_kind` 区分 actual/display/unknown；合计表以 `(currency, value_kind)` 为主键。
**后果**：UI 必须分开展示；未知金额不参与合计；未来跨币种展示需要明确换算来源。

## ADR-008 图表使用 Canvas 2D

**状态**：已采纳
**背景**：不引入图表库；需要主题切换即时重绘与 DPR 适配。
**决定**：`src/web/js/chart.js` 自绘面积图，读取 CSS token 颜色，监听主题事件。
**后果**：交互能力有限（无缩放、无多序列）；关键数值同时以文本呈现。

## ADR-009 实时更新使用 SSE 而非 WebSocket

**状态**：已采纳
**背景**：控制台只需要服务器 → 浏览器的单向推送；聚合仍走 HTTP。
**决定**：`/api/events/stream`，事件 `event` 与 `status`，15s 心跳。
**后果**：浏览器断线自动重连；服务端无状态回放，重连后靠 HTTP 重新取摘要。

## ADR-010 前端使用 hash 路由

**状态**：已采纳
**背景**：本地静态服务无服务端路由；刷新不能 404。
**决定**：`#/live`、`#/history/:id` 等；`app.js` 解析并渲染页面模块。
**后果**：URL 不可 SEO（无需）；可直接分享到本机页面；刷新行为稳定。

## ADR-011 自研 STORE ZIP 读写

**状态**：已采纳
**背景**：分析包需要单文件；不想引入 zip 库；备份也需要归档。
**决定**：`src/shared/zip.mjs` 实现 STORE 方法写入与索引/读取，含 CRC32 与路径穿越防护。
**后果**：无压缩（包体积略大）；读取仅支持 STORE（分析包与未来备份均使用 STORE）；需要更多自测（已覆盖）。

## ADR-012 不接入 AI API

**状态**：已采纳（产品原则）
**决定**：只做文件往返，不做任何 AI 网络调用。
**后果**：用户需要手动操作；分析包必须自包含（提示词 + Schema）；导入端必须做严格校验。

## ADR-013 EXE 资源解压到数据目录（失败回退临时目录）

**状态**：已采纳
**背景**：ESM 与静态资源需要从磁盘加载；安装目录可能只读。
**决定**：解压到 `<数据目录>\app\<hash>\`，不可写时回退到用户临时目录。
**后果**：数据目录含应用副本；升级产生新 hash 目录；需在 M8 增加旧目录清理。

## ADR-014 端口动态选择但不回写设置

**状态**：已采纳（可调整）
**背景**：固定端口易冲突；但用户偏好应稳定。
**决定**：优先 `preferredPort`，冲突时 +1…+9，最后系统分配；本轮不回写实际端口。
**后果**：每次启动可能变化；`runtime.json` 与“已在运行”提示使用实际端口。M8 可考虑记住上次成功端口。

## ADR-015 二维码登录在应用内本地渲染（vendored MIT 库）

**状态**：已采纳

**背景**：Bilibili 扫码登录需要把 `qrcode_key` 对应的 URL 编码成二维码展示给手机扫描。初版把该 URL 交给 Bilibili 的外部页面打开，结果在桌面浏览器中跳转并触发下载，登录不可用。

**决定**：
- 采用与参考项目相同的做法：在页面内生成二维码。
- 使用参考项目自带的 `qrcode.js`（MIT，Kazuhiko Arase），复制到 `src/web/js/vendor/` 并保留 `qrcode.LICENSE.txt`。
- 用 `<canvas>` 自行绘制矩阵，不使用 `innerHTML`；不引入 npm 依赖、不调用任何二维码云服务。
- 服务端只提供二维码内容（`/api/bilibili/login/qrcode`）与轮询（`/api/bilibili/login/poll`），不再打开外部页面。

**后果**：
- 前端多一个约 58 KB 的第三方单文件（MIT，已在仓库内），构建时随 `src/` 一起嵌入 EXE；不需要 `npm install`。
- 二维码生成完全离线，符合「本地优先」与 CSP `script-src 'self'`。
- 若未来升级该库，必须保留版权头与许可证文件，并重跑 `tests/unit/bilibili-qr.test.mjs`。

## ADR-016 YouTube 免登录网页聊天只作为显式实验模式

**状态**：已采纳

> **v0.5.0 备注**：本 ADR 的“官方 API 默认 + 匿名 opt-in”部分已被 **ADR-022** 取代。以下保留为历史决策，不代表当前实现；当前只有公开网页路径。

**背景**：

- 普通用户没有 API Key / Google Cloud / OAuth 客户端，官方路径在默认构建中不可用。
- 公开直播网页有一个无需登录的聊天接口，技术上可行；但它是未公开接口，YouTube ToS 禁止自动化访问与收集可识别个人信息。
- 参考项目 `ytmemchat_wails` 采用“空 Key 用无 Key 客户端、填 Key 只用官方”的模式，但它使用 GPL-3.0，不能复制代码。

**决定**：

1. 保留官方 Data API / OAuth 为默认与推荐路径（`youtubeCaptureMode=official`）。
2. 自行实现 Node ESM 匿名适配器，不复制 GPL/AGPL 代码，不引入 Python/新依赖。
3. 匿名路径必须显式 opt-in；UI 显示“非官方接口、可能与 YouTube 服务条款冲突、可能随时失效”。
4. 不发送 Cookie/OAuth/用户 API Key；不绕过登录、验证码、年龄墙、地区限制。
5. 匿名失败时显示真实原因，不静默切换、不伪造成功。
6. 所有事件仍走 EventIngest；匿名 gift 无 Channel ID 时不建档案。

**后果**：

- 技术目标“用户无需配置 Key 即可读取”在点击一次实验模式后成立；
- 但产品不能声称完全合规，正式发布前需要法律/平台评估；
- 匿名接口变化会导致功能失效，必须保留官方路径作为合规替代。

## ADR-017 YouTube 保留上限收紧为 30 天

**状态**：已采纳

**背景**：旧设置允许 3650 天，但文档同时声称遵守 30 天政策；只删除 `content`/`emotes` 也忽略了 badges、金额显示文本与昵称历史。

**决定**：

- `youtubeRawRetentionDays` 只允许 1–30 天，默认 30。
- 清理 `content`、`emotes`、`badges`、`amount_display` 与过期 YouTube 昵称历史/当前昵称。
- 计数、稳定 Channel ID、金额合计保留；明确这不等同于完全删除个人数据。

**后果**：

- 设置值 31–3650 会被拒绝或钳制到 30；
- 旧库升级后首次启动即按新上限清理；
- 长期观众记忆与严格隐私删除之间仍有取舍，后续需要独立的“严格删除/去标识化”功能。

## ADR-018 启动位置记录与 staging 迁移

**状态**：已采纳（v0.4.0）

**背景**：数据目录可移动到其他磁盘，但启动器必须先找到数据库；把路径存在数据库里不可行。Windows 上 SQLite WAL 直接跨目录复制或就地覆盖有数据一致性风险。

**决定**：

1. 使用独立于数据库的 `data-location.json`（`%LOCALAPPDATA%\LiveMemory`，镜像 `%APPDATA%`），只存路径。
2. 启动时位置记录目标必须已存在且含数据库；否则硬错误，不创建空库。
3. 迁移在目标卷的 staging 目录完成复制与验证（WAL checkpoint、integrity_check、表计数、schema、文件 SHA-256），验证通过后才移入目标、更新位置记录、切换运行时。
4. 原目录永不自动删除；失败回滚目录、位置记录与旧运行时。
5. 单实例锁随数据目录转移（`beginLockMove`）。

**后果**：

- 迁移较慢但可验证、可回滚；需要复制空间（源数据 + 50 MB 余量）。
- 目标必须为空（就 LiveMemory 受管目录而言），不支持合并已有数据空间。
- 映射网络盘只能人工判断；UNC 直接拒绝，OneDrive 等云同步目录需要确认。

## ADR-019 平台全局观众身份 + 主播维度互动档案

**状态**：已采纳（v0.4.0，schema v5）

**背景**：同一平台账号可能出现在多个主播直播间；若把聊天/金额/画像无条件合并，会混淆主播上下文；若复制成多个身份，又会错误拆分同一账号。

**决定**：

- 观众主键仍是 `platform:stable_uid`，昵称不参与身份。
- 主播是独立稳定身份（YouTube channelId；Bilibili anchor uid/room fallback；无法确定则 unresolved）。
- 新增 `(viewer_id, broadcaster_id)` 关系与按主播的币种合计；全局 `viewers` 统计保留为 lifetime。
- UI/API 默认以当前主播为范围；跨主播只显式提供概览；AI 包只导出当前主播的 `broadcaster_context`，其他主播仅给数量。

**后果**：

- 统计需要 scope 参数，不能直接把全局 lifetime 当主播画像。
- 旧 YouTube 场次无法确定主播时保留 unresolved，不猜测；需要未来手动归属 UI。
- 关系表增加跨主播链接性风险；保留/删除策略必须与来源政策一致，不能因新增索引绕过 30 天清理。

## ADR-020 两种删除模式、确认文字与数据库快照

**状态**：已采纳（v0.4.0）

**背景**：用户需要清空记录但保留偏好/登录，也需要真正恢复出厂；不可逆操作必须有明确范围与防误触。

**决定**：

- `data`：删业务表 + 导出 + 缓存；保留设置、凭据、位置记录、`backups/`、日志、根目录无关文件。
- `factory`：额外删偏好/凭据/日志/缓存并重置默认设置；仍保留位置记录、`backups/`、无关文件。
- 必须输入 `DELETE` / `RESET`；记录中禁止；服务端二次校验。
- 删除前可选（默认勾选）数据库应急快照：`VACUUM INTO` 到数据目录之外的 `%LOCALAPPDATA%\LiveMemory-Backups`；明确不是 M5 `.livememory`。
- 数据库在事务中删除后 `VACUUM` + checkpoint，再重建运行时。

**后果**：

- 文件删除是尽力而为；极端中断可能留下部分导出/日志，但数据库为空。
- “清空数据”不会退出平台登录；需要清除授权时用“恢复出厂设置”或平台退出。
- 未来 M5 备份必须使用不同格式，不能把应急快照当作可移植备份。

## ADR-021 原生文件夹选择器使用无管道子进程 + 临时结果文件

**状态**：已采纳（v0.5.0）

**背景**：浏览器无法把任意本地绝对路径交给本地服务；旧实现用 `execFile` 捕获 PowerShell stdout，在受限权限/打包环境中因管道创建失败而 `spawn EPERM`，点击「浏览」直接报错。

**决定**：

- 使用 `spawn(powershell, ['-NoProfile','-STA','-EncodedCommand', base64(script)], {stdio:'ignore', windowsHide:true})`。
- 选择结果写入 `<数据目录>/cache/picker-*.txt`，Node 读取后删除；不使用 stdout/stderr 管道。
- 路径与初始目录用 Base64 嵌入脚本，避免中文、空格、引号与命令注入。
- 取消返回 `null`；脚本错误写 `ERROR:`；超时/spawn 失败分别返回稳定错误码，不吞掉。
- 不做浏览器伪选择器，不要求管理员；手动输入保持。

**后果**：选择器不再依赖管道，兼容受限环境；需要临时目录可写与 PowerShell（Windows 自带）。真实人工点击仍需在有桌面环境验证。

## ADR-022 YouTube 只保留公开网页聊天

**状态**：已采纳（v0.5.0，产品决定）

**背景**：官方 Data API/OAuth 需要开发者配置、配额与登录，且与用户“像 Bilibili 一样直接粘贴链接”的目标冲突；双轨实现增加 UI、测试与维护成本。

**决定**：

- 删除官方 Data API 客户端、OAuth/令牌存储、API Key 配置、官方适配器、`capture-mode` 与相关路由/UI/测试。
- 唯一路径为 `src/platforms/youtube/anonymous/` 公开网页聊天；无需 Cookie/OAuth/API Key。
- 不在正常连接界面显示模式选择或大段实验警告；在设置/隐私说明保留简短、真实的“非官方稳定 API、可能失效、无官方授权”说明。
- 不绕过登录/验证码/年龄墙/地区限制；失败不静默切换。
- schema v5、历史数据、稳定身份与 30 天保留不变。

**后果**：YouTube 接入更简单，但依赖未公开页面结构，可能随时失效；合规风险仍需评估。不得偷偷恢复官方双轨。

## ADR-023 发布 EXE 使用 requireAdministrator Manifest

**状态**：已采纳（v0.5.0，产品决定）

**背景**：用户决定 EXE 默认以管理员权限运行，双击时由 Windows 自动 UAC，而不是要求右键“以管理员身份运行”。

**决定**：

- 构建时直接改写 node.exe 的 PE RT_MANIFEST 为 `requireAdministrator`，不依赖外部 mt.exe/rcedit；新 Manifest 必须放入 `.rsrc` 现有 padding，否则构建失败。
- 开发模式 `node` 不请求管理员；启动器只对打包 EXE 做防御性管理员检查。
- UAC 拒绝发生在程序启动前，Windows 直接终止，EXE 无法捕获；文档不得声称能显示拒绝提示。
- 管理员权限不放宽数据目录校验、迁移 staging/回滚、删除范围。
- 打包启动且当前默认目录无数据库时扫描本地用户配置：恰好一个现有库则使用，多个则拒绝猜测并要求 `--data-dir`。

**后果**：同账号 UAC 通常保持 `%LOCALAPPDATA%`；跨管理员账号的 UAC 会切换用户配置，profile 扫描只是防新建空库的兜底。真实 UAC 批准后的完整流程仍需人工验证。

## ADR-024 多直播间：进程内独立 recording，数据库为真源

**状态**：已采纳（v0.6.0）

**背景**：直播页原假设“同一时间只有一场”。用户需要同时记录多个 YouTube/Bilibili 直播间，且切换页面、关闭浏览器不得停止采集。

**决定**：

- `SessionManager` 用 `Map<sessionId, recording>` 管理任意数量的运行任务；每个 recording 拥有独立 adapter、连接状态、detail、onEnded 与事件闭包。
- 重复启动以 `platform + room` 为键，先查内存、再查数据库 live 行；同步检查后才插入，避免同一进程内竞态。
- 不使用数据库唯一索引限制 live 行，因为需要同时保留多场；单实例锁负责跨进程互斥。
- 所有事件仍只经 `EventIngest`；去重键 `(session_id, dedupe_key)` 允许同一平台消息 ID 在不同场次合法存在。
- 平台服务不再持有唯一 adapter；start/stop 的生命周期归 manager。
- 停止接口按 `sessionId` 精确操作；旧的无 ID disconnect 在多场时拒绝，避免误停。
- 前端标签只读服务端状态；切换用 `viewToken` 丢弃过期响应；不再依赖全局 `livesummary`。

**后果**：任意数量并发受资源而非人为上限约束；1 场失败/停止不影响其他；运行中标签不能关闭，必须先停止（产品选择，避免静默停止或误导）。

## ADR-025 Top 100：单场读模型 + 稳定次级排序

**状态**：已采纳（v0.6.0）

**背景**：原“最活跃观众”只取前 5，数据库查询上限 20；用户需要当前场次 Top 100、搜索、滚动与档案跳转。

**决定**：

- 查询上限 100，排序 `message_count DESC, platform_uid ASC, viewer_id ASC`；昵称不参与身份或次级排序。
- 新 `analytics/sessions/leaderboard.mjs` 只读当前 `session_id` 的 `viewer_sessions`，不读取长期累计或跨主播汇总。
- 搜索在已取出的 Top 100 内过滤，保留原始 `rank`；第 101 名不补位。
- schema v6 新增 `(session_id, message_count DESC)` 索引。
- UI 固定高度滚动容器，默认约 10 行；服务端 rank，不在前端重排；刷新做内容签名与节流。

**后果**：排行榜可复现、不会因同名或同分跳动；跨主播长期统计仍只在观众档案与 AI 包中单独展示。

## ADR-026 启动器控制台默认英文，与网页语言分离

**状态**：已采纳（v0.6.0，用户请求）

**背景**：用户希望双击 EXE 时控制台显示英文；网页界面仍需保留三语与跟随系统。

**决定**：

- `resolveConsoleLocale(options)` 默认 `en`；只有显式 `--lang` 覆盖。
- 启动器不再读取 `settings.json` 的网页语言作为控制台语言。
- 网页界面继续使用 `settings.locale` / 系统语言；两者互不覆盖。
- 三语 CLI 字典保留，`--lang zh-CN|ja` 可切回。

**后果**：控制台输出稳定可读；用户若希望 CLI 中文，需显式 `--lang zh-CN`。文档与截图需说明这一点。

## ADR-027 归档是独立管理属性，结束原因独立于采集状态

**状态**：已采纳（v0.7.0，用户请求）

**背景**：用户需要把旧场次收进归档、随时恢复，同时不能把“我在应用里停止记录”误认为“平台直播结束了”。如果复用 `status`，归档会覆盖采集状态，停止与平台结束也无法区分。

**决定**：

- schema v7 增加 `sessions.archived_at`（NULL = 未归档）与 `sessions.end_reason`（user / adapter 原因 / failed / shutdown / startup_recovery）。
- `status` 只表示本地采集是否有运行中的 adapter；归档不修改 `status`，停止不推断平台状态。
- `POST /api/sessions/:id/archive` 只允许非 live 且无内存 recording 的场次；重复归档保留原时间戳。
- 默认历史列表过滤 `archived_at IS NULL`；`includeArchived=1` / `archivedOnly=1` 显式显示。
- UI 对 `ended + end_reason=user` 显示“已停止记录”，并明确提示平台直播可能仍在继续。

**后果**：归档与采集状态互不覆盖；重启后归档保持；停止记录不再被误描述为平台直播结束。旧数据库升级时两列为 NULL，不猜测历史原因。

## ADR-028 永久删除：事务内删专属行 + 重建衍生聚合

**状态**：已采纳（v0.7.0，用户请求）

**背景**：只删 `sessions` 行会留下孤儿事件/参与关系（若外键被关闭）、过期的观众累计、主播维度和币种合计，以及 AI 包文件。用户明确要求“彻底删除单场，但不得影响其他场次、其他主播档案或无关文件”。

**决定**：

- 单一入口 `session-admin.deleteSessionRecord()`，列表与详情共用；服务端强制 `confirm:true`，拒绝 live 或仍有 adapter 的场次。
- 在 `BEGIN IMMEDIATE` 中显式删除该场次的 `events`、`viewer_sessions`、`session_currency_totals`、`ai_packages`、`sessions`；外键级联保留作为兜底。
- 受影响观众按剩余证据重建：全局计数/首末/币种合计、`viewer_broadcasters`、`viewer_broadcaster_currency_totals`；只存在于该场次的观众删除；`focused=1` 视为用户独立保留数据，保留但计数归零。
- 无场次且无 viewer 关系的 `broadcasters` 行删除；仍有其他场次的主播及其观众档案完全保留。
- 事务内校验所有关联表无残留，失败回滚；提交后才删除 `exports/` 内该场分析包文件，路径必须位于导出根目录。
- 不实现回收站；删除不可撤销。

**后果**：删除后搜索、历史、观众参与列表与 AI 包列表都不会残留该场次；其他场次与主播画像不受影响。数据库删除是原子的，但文件删除是提交后的尽力操作（失败会记录在响应 `fileErrors`，不会让数据库与文件同时处于半删除状态）。未来 M6 的 AI 结果表必须加入同一事务。

## ADR-029 分批 + 第二阶段汇总，而不是让本地规则假装理解整场

**状态**：已采纳（v0.8.0，M6）

**背景**：长时间直播可能有数万条弹幕，任何 AI 都无法稳定一次读完；而跨批次的全场摘要、整体情绪变化与主要争论又需要全局视野。本地规则无法完成语义合并。

**决定**：

- 按 `(occurred_at, id)` 在消息边界拆批（100–5000/批），不截断消息；每批有稳定 `batch_id`、整场 seq 范围、时间覆盖与 `messages.jsonl` 校验和。
- 数据模型保存批次、seq→event 映射与批次观众集合；导入时只接受这些真实引用。
- 单批任务导入即完成；多批任务必须导入全部批次，再生成**第二阶段汇总包**（无原始消息，只含已验证批次结果与全场统计/观众上下文），由用户在任意 AI 完成综合，导入最终结果后才 `complete`。
- 未导入汇总或缺失批次时，报告按批次分别展示并标记“不完整”，绝不把批次结果拼接成整场结论。
- 汇总结果的证据必须写 `{batch, seq}`，避免整数 seq 歧义；汇总包不会自动调用 AI，也不会由本地规则伪造合并结果。

**后果**：长直播可以分次完成；用户仍然完全掌控交给哪个 AI；代价是多批任务多一次 AI 往返，且用户必须显式完成汇总。部分结果不会被误标为完整分析。

## ADR-030 AI 结果是外部输入：版本只追加，身份/证据必须可验证

**状态**：已采纳（v0.8.0，M6）

**背景**：AI 返回的 JSON 不能信任：可能编造昵称、消息、时间、观众，夹带 HTML/脚本，或重复导入导致重复统计；同一任务也可能被用户主动重新分析。静默覆盖会丢失审计线索。

**决定**：

- 结果进入独立的 `ai_results` / `ai_result_evidence` 表，按 `(job_id, scope_key)` 追加版本；相同规范化内容（SHA-256）判重复不写，不同内容必须显式 `createVersion`。
- 结果按字段白名单重建、清除控制字符；UI 只用 `textContent`，不执行任何 AI 内容；结果不能写事件、金额、计数或设置。
- 身份只按稳定 `viewer_id` 解析；昵称不参与匹配；批次观众集合与任务内并集分别限制批次/汇总结果；不得跨主播合并。
- `message_refs` 必须命中 `ai_job_messages`；报告从真实 `events` 读取原文，清理/删除时标记不可用。
- 任务状态由数据库实时计算；部分结果不得标记 complete；删除场次/清空数据必须覆盖全部 AI 表与文件。
- M6 的 `viewer_profiles` 是场次级衍生数据；YouTube 30 天清理不会自动删除它，须在 M7 前补齐保留/去标识化策略。

**后果**：重复上传不会重复统计，重新分析保留旧版本，错误结果可审计；代价是结果表和证据表随场次增长，且长期 AI 画像的保留问题仍未解决（已知限制）。

## ADR-031 平台直播状态与本地采集状态分离，多信号确认下播

**状态**：已采纳（v0.8.1，schema 9）

**背景**：Bilibili 下播后 WebSocket 仍保持连接，离线房间也可能有零散聊天；
旧实现把“采集任务在运行”当成“平台在直播”，导致下播后永久显示直播中、时长无限增长。
但只看弹幕密度、连接状态或单次 `live_status` 都会误判：主播可能长时间不说话，
网络可能断开，接口可能 429/风控。

**决定**：

- `sessions.status` 只描述本地采集；新增 `platform_status` 等列描述平台状态。
- Bilibili 同时使用 WebSocket `LIVE`/`PREPARING`/`STOP_LIVE` 与定期 `live_status` 查询。
- 确认规则：WS 下播事件 + 1 次有效离线查询，或 2 次连续有效离线查询；
  超时/429/-352/缺字段/房间不匹配/无效值只退避，绝不结束。
- 自动结束只停止对应场次，清定时器/WS/重连，写最终事件，保留全部数据；
  快速重开创建新场次，旧回调不能写入新场次。
- `platform_ended_at` 只在有证据时写；历史修复/启动恢复不编造结束时间，
  不用最后一条弹幕时间代替。
- 历史修复只处理崩溃/退出遗留行，当前 live 不污染旧场次，幂等且有日志。

**后果**：下播能在合理时间自动结束，其他直播不受影响；代价是每个 Bilibili 房间多一个
周期 HTTP 查询，且平台接口长期风控行为仍需观察。真实“直播中→下播”端到端样本仍待捕获。

## ADR-032 自动监听以持久目标为中心，YouTube 用公开频道页而非官方 API

**状态**：已采纳（v0.10.0，schema 11）

**背景**：用户要求“添加一次直播间/频道，软件长期自动记录每一场”，且 Tab 必须跨场保留。
现有 Tab 完全由 active recording 派生，关播即消失；YouTube 视频 ID 每场不同，不能作为监听目标。
同时用户明确不把 Google Data API/OAuth/API Key 作为默认前提，要求优先研究开源方案。

**决定**：

- 新增 `monitor_targets` 作为持久目标（Bilibili 房间 / YouTube 频道），`sessions` 仍是单场记录；
  `sessions.monitor_target_id` 只是关联，不做级联删除。目标是 Tab 的数据源，关播不删除目标。
- 监听状态机独立于适配器连接状态；`reconnecting` 是公开派生状态，数据库仍为 `recording`，
  网络重连不得创建新场次。只有确认新的 `live` 才创建新 session。
- 统一 `MonitoringManager` 负责调度/退避/会话创建；平台差异只在 detector：
  Bilibili 用公开 `room_status`；YouTube 用公开 `/channel/<id>/live` + `ytInitialPlayerResponse`，
  解析失败时 RSS + watch 页确认回退。
- YouTube 不引入 streammon（无 LICENSE，不能复制）、livestream_saver（GPL-3.0，不兼容）、
  yt-dlp/pytchat（Python/外部进程，已有同类聊天实现）；只参考公开事实与 yt-dlp 的
  `live_status` 语义。零运行时依赖不变。
- 等待开播才轮询；记录中不重复轮询。Bilibili 约 60 秒、YouTube 约 180 秒，带抖动、
  每平台串行 pacer、指数退避与 `Retry-After`；连续失败进入可见 `error`。

**后果**：Tab 与目标长期稳定，自动场次完全复用 M6/M7；代价是 YouTube 依赖公开页面结构，
页面改版可能触发 RSS 回退或显式错误，检测延迟最长约 2–4 分钟。真实长期稳定性仍需观察，
不能描述为 YouTube 官方/稳定 API。

## ADR-033 监听目标删除与场次删除互不级联

**状态**：已采纳（v0.10.0）

**背景**：监听目标与单场记录是两个生命周期；用户可能想停止监听但保留历史，也可能删除某场但继续监听。

**决定**：

- 删除目标：拒绝于记录中；否则删除目标行，并把该目标的 `sessions.monitor_target_id`
  置空（历史保留），同时清空目标上的 `active_session_id`/`last_session_id`。
- 删除场次：事务删除场次专属数据，但只清空目标上的指针，**不删除目标**。
- 清空全部数据/恢复出厂：目标与场次一起删除。
- 暂停监听不停止当前记录；停止当前记录不删除目标。

**后果**：用户不会因为整理 Tab 或删除一场而意外丢失长期监听配置，也不会因为删除监听目标而丢失历史；
代价是 UI 必须明确区分四种操作（关闭 Tab / 暂停 / 停止记录 / 删除目标），并在记录中禁止删除目标。

## ADR-034 长期记忆并入 AI 分析结果，客观历史与语义记忆分离

**状态**：已采纳（v0.11.0，schema 12）

**背景**：v0.9.0 的 M7 把长期记忆做成独立的第二次 AI 工作流：先做本场分析，再导出记忆更新包。
同时旧提示词明确要求“证据不足的观众请省略”，本地合并只消费 `viewer_profiles`，导致实际只更新
少数高活跃观众。用户要求一次导出/一次 AI/一次导入，并覆盖每一位可识别观众。

**决定**：

- 在同一个 `livememory-analysis-result-v1` 中新增 `viewer_memory_updates`（Schema 1.2.0）；
  分析包新增 `memory_context.json` 与 `viewer_excerpts.jsonl`。一次导入在同一事务中保存报告与记忆。
- 每个可识别观众只分配到一个记忆批次，其全部可用发言（最近 120 条）随批次导出；
  批次由消息量与观众数共同决定，观众上限 20000 并显式报错，不静默截断。
- 每位观众的语义更新条目是**强制**的：没有新语义时必须返回空 operations + `no_new_information: true`；
  缺少条目是导入错误，不是静默跳过。
- 客观互动历史（首次/最近、场次、发言数、支持）由真实表确定性更新，AI 不能输出或修改；
  没有语义事实时仍创建/保留 version 0 的记忆头。
- 取消独立 `#/memory` 页面与导航；旧链接进入 AI 分析中心。观众详情保留长期记忆标签并新增客观历史卡。
- 旧 1.0/1.1 结果仍可导入，但只更新客观历史（`objective_only`）；旧 M7 记忆任务表保留历史，不再由 UI 创建。

**后果**：一次文件往返即可得到本场报告与全部观众的持续记忆；代价是分析结果更大、AI 必须严格覆盖
批次内每位观众，且 1.2.0 之前的回答不会产生新的语义记忆。真实 AI 是否能稳定返回完整覆盖仍需样本验证；
对未验证的真实平台/真实 AI 结果，不得描述为已验收。

## ADR-035 自动分析只接入实测通过的匿名 provider，并复用现有导入路径

**状态**：已采纳（v0.12.0）

**背景**：用户要求“点一次自动 AI 分析”完成报告与长期记忆，同时不要求用户申请 Key/注册/付费，
也不允许开发者维护云端代理或提供自己的 Key。候选匿名接口必须先实测，不能假设仍有效。

**决定**：

- 先做真实网络测试，再决定集成：OVHcloud AI Endpoints `gpt-oss-20b` 匿名通道
  （官方 2 请求/分钟/IP/模型）通过真实 LiveMemory 包；Murakumo、llmfaucet、LLM7、Pollinations
  未通过，**不进入自动列表**。证据见 `docs/ANONYMOUS_AI_RESEARCH.md`。
- 不引入付费 Key、账号、开发者代理或新的运行时依赖；只用 Node 内置 `fetch`、`AbortSignal`。
- 自动任务仍由 `createAnalysisJob()` 生成批次；使用更小的自动上限（250 消息/25 观众/600 摘录、
  最多 12 批），以保证免费服务的上下文与输出预算；超出时明确失败，不裁剪观众。
- 每个回答必须先 `validateAnalysisImport()` 通过，再 `importAnalysisResult({source:'auto'})`；
  不新增直接写 `ai_*`/`events` 的路径，不降低 Schema/证据/覆盖率要求。
- 只允许一次修复、一次网络重试、单次运行请求预算；429 尊重 `Retry-After`。
- 首次使用必须明确同意发送当前分析数据；不发送数据库文件、凭据或不相关直播。
- 失败时只显示固定红色文案 + 折叠详情；不删除已完成结果、不覆盖已有记忆、不自动切换手动模式。

**后果**：用户获得零配置的一键入口，同时保留全部手动流程；代价是当前只有一个 provider，
受 2 请求/分钟限制，且免费服务可能限流/下线。自动失败时任务状态与已导入批次仍保留，
可恢复或改用手动流程；不能把“历史测通”描述为“永久可用”。
